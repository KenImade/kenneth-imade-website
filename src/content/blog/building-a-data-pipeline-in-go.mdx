## Why Go for Data Pipelines

Most data engineering tooling defaults to Python. It's where the ecosystem lives — Airflow, dbt, Pandas, Spark bindings. But Python has a ceiling. Once your pipeline is processing millions of events per hour, you start paying for it in CPU and memory.

Go gives you goroutines, channel-based concurrency, and a runtime that doesn't fight you when you need to squeeze performance. It also compiles to a single binary, which makes deployment embarrassingly simple.

The tradeoff is you lose the data ecosystem. No Pandas, no NumPy, no notebooks. You're writing transforms by hand. For the right use case — high-throughput, low-latency, operationally simple — that's a trade worth making.

## The Architecture

The pipeline we're building has three stages:

1. **Ingestion** — read events from a Kafka topic
2. **Transform** — validate, enrich, and reshape each event
3. **Load** — write batches to PostgreSQL

Each stage runs concurrently, connected by buffered channels. Backpressure is handled naturally — if the loader is slow, the channel fills, and the transformer blocks until there's room.

### Ingestion

We use `confluent-kafka-go` to consume from Kafka. Each message is decoded from JSON and pushed onto a channel:

```go
func ingest(ctx context.Context, consumer *kafka.Consumer, out chan<- Event) {
    for {
        select {
        case <-ctx.Done():
            return
        default:
            msg, err := consumer.ReadMessage(100 * time.Millisecond)
            if err != nil {
                continue
            }
            var e Event
            if err := json.Unmarshal(msg.Value, &e); err != nil {
                log.Printf("decode error: %v", err)
                continue
            }
            out <- e
        }
    }
}
```

The timeout on `ReadMessage` keeps the goroutine responsive to context cancellation — you don't want a pipeline that ignores shutdown signals.

### Transform

The transform stage reads from the ingestion channel, applies business logic, and pushes results to the load channel:

```go
func transform(in <-chan Event, out chan<- Record) {
    for e := range in {
        r, err := toRecord(e)
        if err != nil {
            log.Printf("transform error: %v", err)
            continue
        }
        out <- r
    }
}
```

Keeping transforms pure functions makes them trivial to test. `toRecord` takes an `Event` and returns a `Record` — no side effects, no globals.

### Loading

The loader collects records into batches and writes them to Postgres using `pgx`:

```go
func load(ctx context.Context, pool *pgxpool.Pool, in <-chan Record) {
    batch := make([]Record, 0, 500)
    ticker := time.NewTicker(5 * time.Second)
    defer ticker.Stop()

    flush := func() {
        if len(batch) == 0 {
            return
        }
        if err := insertBatch(ctx, pool, batch); err != nil {
            log.Printf("insert error: %v", err)
        }
        batch = batch[:0]
    }

    for {
        select {
        case r, ok := <-in:
            if !ok {
                flush()
                return
            }
            batch = append(batch, r)
            if len(batch) >= 500 {
                flush()
            }
        case <-ticker.C:
            flush()
        case <-ctx.Done():
            flush()
            return
        }
    }
}
```

The dual flush condition — batch size or time — means you don't accumulate unbounded memory, and low-traffic periods still get written within five seconds.

## Observability

A pipeline without metrics is a black box. We export three things:

- **Throughput** — events ingested, transformed, and loaded per second
- **Lag** — how far behind the pipeline is from the Kafka consumer group offset
- **Error rate** — decode errors, transform errors, insert errors separately

We use `prometheus/client_golang` and expose a `/metrics` endpoint. Nothing exotic — counters and gauges, scraped by a local Prometheus instance, visualised in Grafana.

### Structured Logging

`log.Printf` is fine for development but painful in production. We switch to `slog` (standard library since Go 1.21) with JSON output:

```go
logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
logger.Info("batch flushed", "count", len(batch), "duration_ms", elapsed.Milliseconds())
```

Every log line has a timestamp, level, message, and structured fields. CloudWatch, Loki, or whatever log aggregator you're using can index on those fields.

## Error Handling

The instinct is to retry on error. But retrying blindly creates problems — if a record is fundamentally malformed, retrying it a thousand times just burns CPU.

We use a dead letter pattern: records that fail transform go to a `dlq` channel, which a separate goroutine drains to a `pipeline_dlq` table. You can inspect bad records, fix the transform, and replay them. This keeps the main pipeline moving and gives you an audit trail.

## Graceful Shutdown

Shutdown order matters. You can't close the ingestion channel while the transformer is still reading from it — you'll panic.

We use a context with cancel for signals, and close channels in the correct order once each stage drains:

```go
ctx, cancel := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer cancel()

inCh := make(chan Event, 1000)
outCh := make(chan Record, 1000)

var wg sync.WaitGroup
wg.Add(3)

go func() { defer wg.Done(); ingest(ctx, consumer, inCh); close(inCh) }()
go func() { defer wg.Done(); transform(inCh, outCh); close(outCh) }()
go func() { defer wg.Done(); load(ctx, pool, outCh) }()

wg.Wait()
```

When the context is cancelled, `ingest` exits and closes `inCh`. The transformer drains `inCh`, then closes `outCh`. The loader drains `outCh`, flushes the final batch, and exits. Clean.

## What I'd Do Differently

Running this in production for a few months, a few things stand out:

- **Schema validation at ingestion** — catching malformed events early, before the transform stage, reduces noise in the DLQ
- **Separate concurrency for transform** — a single goroutine works but adding a worker pool (via `errgroup`) gives you easy horizontal scaling within the process
- **Backoff on insert failures** — the current loader logs and continues; a transient Postgres hiccup can cause data loss during a bad window

These aren't blockers — the pipeline has been reliable — but they're the things I'd build differently from scratch.
